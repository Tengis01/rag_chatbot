\section{Онолын мэдлэгийг практикт хэрэгжүүлсэн байдал}

Энэ төслийг хийхдээ их сургуульд үзсэн өгөгдлийн сан, алгоритмын мэдлэгээ
ашиглаж, RAG, embedding, вектор хайлтын талаар нэмж судалсан. Судалсан
аргаа кодод хэрэглэхэд томьёог ойлгохоос гадна өгөгдлийн бүтэц, тооцоолох
дарааллыг сонгох шаардлагатай байв. Тухайлбал, MMR-ийн томьёог greedy
алгоритмаар хэрэгжүүлж, өмнө сонгосон хэсгүүдтэй давхцах байдлыг хэмжих
$sim_2$-ийн үүрэгт Jaccard хэмжигдэхүүнийг ашигласан.

Олон хэлний embedding ашигласан ч хэл дамнасан хайлтын чанарыг тусад нь
шалгах хэрэгтэйг туршилтаас ойлгосон. Кирилл баримт, латин асуултын хос дээр
төстэй байдлын утга ойролцоогоор $0.35$ гарсан нь анх сонгосон босгоос бага
байв. Иймээс загварын олон хэлний дэмжлэгт найдаад тохиргоог хэвээр үлдээх
боломжгүй байсан. Босгыг өөрчилж үр дүнг харьцуулсан энэ туршилт нь
онолын тайлбарыг өөрийн өгөгдөл дээр шалгаж сурахад тустай байлаа.

Мөн төлбөртэй үйлчилгээ ашиглах төсөвгүй байсан тул технологи сонгохдоо
үнэгүй түвшний хязгаар, ажиллуулах орчин, нэмэлт хамаарлыг хамтад нь
тооцсон. Сонголтын шалтгаан болон үлдсэн хязгаарлалтыг тэмдэглэж хэвшсэн.

\section{Инженерийн дадал, хэрэглэсэн технологи}

Сервер талд Fastify, TypeScript ашиглан API бичиж, кодыг үйл ажиллагаагаар
нь модулиудад хуваасан. PostgreSQL-тэй шууд SQL-ээр ажиллахдаа холбоотой
өгөгдлийг транзакц дотор хадгалах, бүтцийн өөрчлөлтийг migration файлаар
оруулах аргыг хэрэглэж сурсан. Вектор хайлтад pgvector өргөтгөл болон HNSW
индексийг тохируулж ашиглав.

Гадаад API-ийн хүсэлт бүр амжилттай болохгүйг том текст боловсруулах үед
ажигласан. Хүсэлтүүдийг багцлах, хүлээх хугацааг хязгаарлах, алдааны дараа
завсарлагатай дахин оролдох хэрэгтэй болсон. Эдгээрийг хэрэгжүүлэх явцад
алдааны хариунаас шалтгааныг нь ялгаж, дахин оролдох эсэхийг шийдэх
туршлагатай болсон.

Клиент талд React-ийн мэдлэгээ вэб болон React Native, Expo дээрх мобайл
аппад ашигласан. Хоёр клиент нэг API-тай ажилладаг тул хариу өгөгдлийн бүтэц,
баримтын төлөв шалгах логикийг нийцүүлэх шаардлагатай байв. Бодит утсан дээр
туршихад эмулятороос ялгаатай сүлжээний хаяг, дэлгэц гүйлгэх болон хажуугийн
цэс нээх хөдөлгөөний зөрчил зэрэг асуудал гарсан. Эдгээрийг засахдаа зөвхөн
эмулятор дээр шалгах нь хангалтгүйг ойлгосон.

Better Auth-аар нэвтрэлт хийхдээ session шалгалт, нууц үгийн hash,
хэрэглэгчийн өгөгдлийг \texttt{user\_id}-аар шүүх аргуудтай ажилласан.
Нэвтэрсэн эсэхийг шалгахаас гадна хүссэн баримт нь тухайн хэрэглэгчийнх
мөн эсэхийг шалгах шаардлагатайг анхаарч сурсан. Мөн Docker Compose-оор
үйлчилгээнүүдийг хамт ажиллуулах, build cache ашиглах Dockerfile бичих,
pnpm болон Turborepo-оор monorepo удирдах дадлага хийв.

\section{Асуудал шийдэх, баримтжуулах арга барил}

6-р бүлэгт тайлбарласан алдаануудыг засахад нэг шинж тэмдэг хэд хэдэн
шалтгаантай байж болохыг анзаарсан. Би клиент, API, өгөгдлийн сангийн
ажиллагааг тус тусад нь шалгаж, лог болон хүсэлтийн хариуг харьцуулан
шалтгааныг нь хайсан. Контейнер засварласан кодыг уншаагүй тохиолдол ч
гарсан тул эхлээд яг ямар код ажиллаж байгааг шалгах хэрэгтэй болсон.

Алдааг ERR-NNN дугаараар бүртгэж, шинж тэмдэг, шалтгаан, засварыг нь хамт
тэмдэглэсэн. Технологийн сонголтыг мөн үндэслэлтэй нь хадгалсан нь өмнөх
ажлаа үргэлжлүүлэхэд хэрэг болсон. Жишээлбэл, хайлтын босгыг бууруулсан
шалтгаан болон энэ нь түр шийдэл гэдгийг бүртгэлээсээ эргэн харах боломжтой.

Өөрчлөлтөө шалгахдаа smoke тест, typecheck, build ашиглаж, мобайл
интерфэйсийг утсан дээр туршсан. Туршилтын үр дүнг бичихдээ амжилттай
дууссан болон шалгаж амжаагүй хэсгийг ялгаж тэмдэглэв. Тухайлбал, 500
мянган тэмдэгттэй текстийн боловсруулалт тасалдсан тул дуусах хугацааг нь
хэмжсэн үр дүн гэж үзээгүй.

Ажлаа удирдагчаар батлуулсан төлөвлөгөөний дагуу хэсэгчлэн гүйцэтгэж,
хэрэгжүүлэх явцад өөрчилсөн технологи, хойшлуулсан ажлын шалтгааныг
тэмдэглэж явсан. Энэ нь тайлан бичих үед төлөвлөсөн болон хийсэн ажлаа
тулган харахад тусалсан.
